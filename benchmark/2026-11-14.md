# Single-node MQTT benchmarks, November 14, 2026

These measurements cover the default-feature release build of [IndraMQTT at commit `2342a432`](https://github.com/ankur-paan/indramqtt/commit/2342a432c0e300b56e4bcc3a223608b96232a30f). The broker had four pinned CPUs and an 8 GiB memory limit on an Intel Xeon E5-2697A v4 host. The load generators used separate CPUs on the same host and connected over plaintext TCP loopback. The tables summarize the confirmation records and repeated runs in appendices A and B of the November 14 performance report.

## MQTT 3.1.1 with and without a SQL rule

Each build ran five times per workload, alternating the November build with the October 25 baseline. Each run lasted 120 seconds. There were 1,000 publisher/subscriber pairs, one topic per pair, 128-byte payloads, and QoS 0.

| Workload | Offered messages/s | October build, median delivered/s | November build, median delivered/s |
| --- | ---: | ---: | ---: |
| Plain routing | 125,000 | 121,793 | 121,757 |
| Routing with SQL republish | 50,000 | 48,714 | 48,700 |

The rule ran `SELECT * FROM "t/#"` and republished each match to `d6/out`. The rate counts messages delivered to the original subscribers. The output topic had no subscriber. All 20 runs passed the delivery checks with zero recorded loss. The November rule runs delivered 48,715, 48,680, 48,681, 48,742, and 48,700 messages/s. The two workloads used different offered rates, so their medians cannot establish the throughput cost of enabling SQL.

## MQTT 5 broker comparison

IndraMQTT and EMQX Enterprise 6.3.0 each ran in a fresh container for each step, using 256-byte payloads. EMQX used its default configuration. A 45-second search selected a load for a nominal 180-second confirmation. A passing step had to meet the harness’s rate, delivery, latency, memory growth, and drain checks. Delivered rates include drain time. Fan-out counts deliveries to subscribers.

| Workload | IndraMQTT offered/s | IndraMQTT delivered/s | EMQX offered/s | EMQX delivered/s |
| --- | ---: | ---: | ---: | ---: |
| Point-to-point, QoS 0 | 200,000 | 184,829 | 80,000 | 79,692 |
| Point-to-point, QoS 1 | 80,000 | 79,353 | 25,000 | 24,947 |
| Fan-in, QoS 0 | 50,000 | 49,648 | 20,000 | 19,946 |
| Fan-out, QoS 0 | 100,000 | 99,442 | 80,000 | 79,748 |

- **Point-to-point QoS 0.** All 36 million IndraMQTT messages arrived. Publishing took 193.7 seconds and the drain took 1.1 seconds. The harness counted ten publisher CPUs, but only nine were available. The publisher saturated and the broker also approached its CPU limit, leaving the broker ceiling undetermined.
- **Fan-out.** IndraMQTT confirmed 10,000 subscribers. At the next step only 11,183 of 12,000 completed subscription, leaving the ceiling undetermined. EMQX confirmed 8,000 subscribers. At 10,000 it delivered 99,663/s, but its memory grew beyond the harness threshold.
- **Comparison scope.** Each confirmation ran once, with IndraMQTT tested first in each scenario. Run-to-run variation is unknown. The four-core comparison covers these two brokers, plaintext connections, and one payload size. The [October one-CPU study](README.md) also includes rumqttd, with a different IndraMQTT build and memory limit.

## Memory at the same client count

Both brokers connected all 10,000 idle clients. The harness read broker-container memory with `docker stats`. These figures apply to this build and connection workload.

| Measurement | IndraMQTT | EMQX Enterprise 6.3.0 |
| --- | ---: | ---: |
| Before clients connected | 5.6 MiB | 430.9 MiB |
| After 30 seconds with 10,000 connected | 186.3 MiB | 842.3 MiB |
