# Single-node MQTT benchmarks, November 14, 2026

These measurements cover the default-feature release build of [IndraMQTT at commit `2342a432`](https://github.com/ankur-paan/indramqtt/commit/2342a432c0e300b56e4bcc3a223608b96232a30f). The broker had four pinned CPUs and an 8 GiB memory limit on an Intel Xeon E5-2697A v4 host. The load generators used separate CPUs on the same host and connected over plaintext TCP loopback. The tables summarize the confirmation records and repeated runs in appendices A and B of the November 14 performance report.

## MQTT 3.1.1 with and without a SQL rule

Each build ran five times per workload, alternating the November build with the October 25 baseline. Each 120-second run used 1,000 publisher/subscriber pairs, one topic per pair, 128-byte payloads, and QoS 0. **All 20 runs recorded zero message loss.** The table gives the median rate at which the original subscribers received messages.

| Workload | October build, messages/s | November build, messages/s |
| --- | ---: | ---: |
| Plain routing | 121,793 | 121,757 |
| Routing with SQL republish | 48,714 | 48,700 |

Each publisher was scheduled to send once every 8 ms for plain routing and every 20 ms with the rule active. Those different intervals limit throughput comparisons between the two workloads.

The rule ran `SELECT * FROM "t/#"` and republished each match to `d6/out`. The output topic had no subscriber. The November rule runs delivered 48,715, 48,680, 48,681, 48,742, and 48,700 messages/s.

## MQTT 5 broker comparison

**Subscribers received all 36 million messages in IndraMQTT’s point-to-point QoS 0 confirmation run.** The generator scheduled the batch for 180 seconds. It took 193.7 seconds to send it, and the remaining messages reached subscribers 1.1 seconds later. Across that elapsed time, throughput averaged **184,829 messages/s**. The publisher used all nine CPUs available to it, and the broker also approached its CPU limit. The broker’s maximum throughput remains undetermined.

The table shows measured delivery rates at each broker’s highest passing load for each workload. **Both brokers recorded zero loss in every run shown.** Rates include the time for the last messages to arrive. Fan-out counts each delivery to a subscriber.

| Workload | IndraMQTT deliveries/s | EMQX Enterprise 6.3.0 deliveries/s |
| --- | ---: | ---: |
| Point-to-point, QoS 0 | 184,829 | 79,692 |
| Point-to-point, QoS 1 | 79,353 | 24,947 |
| Fan-in, QoS 0 | 49,648 | 19,946 |
| Fan-out, QoS 0 | 99,442 | 79,748 |

Each step used a fresh container and 256-byte payloads. EMQX used its default configuration. A 45-second search selected a load for a nominal 180-second confirmation. Passing required complete delivery as well as checks on rate, latency, memory growth, and drain time. The harness counted ten publisher CPUs when nine were available, so its saturation flag missed the QoS 0 generator limit.

| Point-to-point, QoS 1 | 800 pairs | 250 pairs |

| Fan-out, QoS 0 | 10,000 subscribers | 8,000 subscribers |

</details>

- **Fan-out.** IndraMQTT confirmed 10,000 subscribers. At the next step only 11,183 of 12,000 completed subscription, leaving the ceiling undetermined. EMQX confirmed 8,000 subscribers. At 10,000 it delivered 99,663/s, but its memory grew beyond the harness threshold.
- **Comparison scope.** Each confirmation ran once, with IndraMQTT tested first in each scenario. Run-to-run variation is unknown. The four-core comparison covers these two brokers, plaintext connections, and one payload size. The [October one-CPU study](README.md) also includes rumqttd, with a different IndraMQTT build and memory limit.

## Memory at the same client count

Both brokers connected all 10,000 idle clients. The harness read broker-container memory with `docker stats`. These figures apply to this build and connection workload.
